# Provider Package

## Purpose

The provider package is the **foundational interface** for CANI. All inventory providers must implement this interface to integrate with the system. Providers follow an **ETL (Extract-Transform-Load)** pattern for syncing external inventory sources with CANI's internal datastore.

## Layout

| File | Purpose |
|------|---------|
| `interface.go` | Core `Provider` interface and optional extension interfaces |
| `struct_to_map.go` | Reflection utility for converting structs to maps |

## Core Interface

Every provider must implement `Provider`:

| Method | Purpose |
|--------|---------|
| `Transform` | Convert external data to CANI format (Transform step) |
| `NewProviderCmd` | Return provider-specific CLI commands |
| `Slug` | Return provider identifier |

## Optional Interfaces

Providers implement only the capabilities they support; the command layer
type-asserts each one, so unimplemented interfaces degrade gracefully:

| Interface | Purpose |
|-----------|---------|
| `Importer` | Extract data from an external system or source (Extract step) |
| `Exporter` | Sync local inventory to an external system (Load step) |
| `HasOptions` | Expose default configuration options |
| `Configurer` | Receive and validate the provider's config section at startup |
| `HasImportOptions` | Import-specific config/flags |
| `HasExportOptions` | Export-specific config/flags |
| `DeviceStager` | Auto-stage an existing device during `add` |
| `RackStager` | Create a new device hierarchy under a staged rack |
| `RackPostAddHook` | Run provider logic after a rack is added |
| `DeviceUpdateFlagProvider` | Contribute provider-specific `update device` flags |
| `StagedDeviceDescriber` | Supply human-readable staged-device description lines |
| `ExportDryRunner` | Report a dry run resolved from the provider's own config so `export` skips the save |
| `IdentityKeyProvider` | Name the keys in the provider's bucket that identify one physical device, the same ones its `Transform` declares on `TransformResult.IdentityKeys` |

See [CAPABILITIES.md](CAPABILITIES.md) for the current matrix of which provider
implements which optional interface. The matrix is verified and regenerated by
the conformance suite in `conformance/conformance_test.go`.

## Provider Registry

- `Register(name, provider)` — Called in provider's `init()` to register. `name` is the slug and
  the name of the provider's bucket; `Register` tells the model (`devicetypes.RegisterProviderBucket`)
  that the bucket has an owner, so a bucket named for no built-in provider is reported on load
- `GetProvider(name)` — Retrieve a registered provider
- `GetProviders()` — Get all registered providers
- `IdentityKeys()` — The identity keys every registered `IdentityKeyProvider` declares, as one
  sorted list; `update orphans` scores candidate parents by them

## Implementing a New Provider

1. Create a new package under `pkg/provider/<name>/` via `cani init <new-provider-name>`
2. Implement the `Provider` interface
3. Call `provider.Register("<name>", &YourProvider{})` in `init()`
4. Implement optional interfaces as needed (`Importer`, `HasOptions`, etc.)
5. Keep methods focused—each should do one thing well

## Transform Output Contract

`Transform` returns a `devicetypes.TransformResult` of shared types; the command layer merges it
through `Inventory.MergeTransformResult`, which validates relationships and refuses the whole
result on an error. The merge applies the same rules to every provider:

- A source record the provider cannot translate is left out and listed in `TransformResult.Warnings`,
  one line each; the command layer prints and counts them. Do not invent a value to keep the record.
- `CaniModuleType.ModuleBayName` is a bay the parent device (or its library type) declares. The
  merge canonicalises the spelling and clears a bay the parent does not declare, reporting it for
  the operator; it never persists an undeclared bay, because export would otherwise create it in
  the target system. A provider that knows the bays its source system declares for a device sets
  `CaniDeviceType.ModuleBays` (name and position), so those names are declared for that instance
  and survive the merge; the library template is consulted only for a device that declares none.
  A provider that only knows its own placement descriptor (a tray or slot
  number, for example) leaves `ModuleBayName` empty and keeps the descriptor in `ProviderMetadata`.
- Each value has one home, and the merge, the generic commands and other providers' exports read
  it from that home only:
  - An attribute the shared model has a field for goes in the field (`Role`, `Status`, `Location`,
    `UHeight` and so on), even when the provider also keeps its own copy. Only the provider
    itself reads a role or a location from its bucket.
  - An attribute the source system's operators define (a Nautobot custom field) goes in
    `CustomFields`, with its definition in `TransformResult.Metadata`. A provider does not use
    `CustomFields` for its own records.
  - What only the provider needs goes in its own bucket, `ProviderMetadata[<slug>]`, written with
    `SetProviderMeta(slug, key, value)`: never as a new field on a shared type, never in another
    provider's bucket, and never beside the buckets, where nothing reads it and every command
    that changes the inventory reports it.
  - The source system's ID for the object goes in `ExternalIDs[<slug>]`.
- A provider reads its own bucket with `GetProviderSubMap(slug)`. There is no lookup across
  buckets, with one exception: an identity key. A provider whose bucket holds a key that names
  one physical device (CSM and OChaMi `xname`, Redfish `bmc_fqdn` and `bmc_hostname`) declares
  it on `TransformResult.IdentityKeys` and answers for it through `IdentityKeyProvider`.
  Declaring a key asserts it means the same thing in every bucket that holds it, so the merge
  compares declared keys across buckets when two devices share a name, and
  `CaniDeviceType.IdentityValue(key)` reads one from whichever bucket holds it, as the OChaMi
  export does for the `xname`. Anything else in another provider's bucket is that provider's
  record; reading it is a dependency on that provider and names it.
- A module is matched to an existing one by external ID, then by identity (asset tag, or serial on
  the same type when both record one), then by name. An incoming module whose identity names two
  existing modules is a conflict; the merge refuses the whole result rather than choosing one.
